What happens when one AI tries to break another AI’s backtest?

Two Muse Spark agents with opposite jobs. The final verdict comes from code, not the model.

Built from scratch in a 10-day hackathon: a research agent hunts for a good backtest, an auditor agent attacks it, and a sealed holdout is opened exactly once.

0.32→ 0.30

The auditor’s logged holdout prediction, then the actual Sharpe when the hash-sealed holdout was opened. The model still called the strategy SURVIVES; the code rubric said FRAGILE.

Situation
AI research assistants never get tired of trying variants, so they make overfit backtests faster. A team needs to know whether a result is real before money follows it.
What I did
Designed the system and the evaluation, and directed the build with AI coding tools (logged in the repo). A research agent iterates on in-sample data only; an auditor agent runs walk-forward, Deflated Sharpe, PBO and cost-stress tests by tool call, writes down a prediction, then opens the holdout once. A notebook mode finds look-ahead leaks and proves each one with a test.
Outcome
In the live run the model mostly refused to overfit. The one exception was a trial that set trading costs to zero, and it became the in-sample winner (Sharpe 0.68). Holdout: 0.30. Deflated Sharpe 0.04, verdict FRAGILE.
Code and README on GitHub
Guardrails
Strategies are JSON specs, never code · signal at t uses data up to t−1 · holdout (2024 onward) hash-sealed, opened once · every number from deterministic code
Notebook mode
A finding counts as PROVEN only if a generated test fails on the original code, passes with the fix, and passes on a clean control notebook

The most useful result was a failure of our own: an early baseline scored 0.62 precision and 1.00 recall only because it matched our example variable names. The held-out set caught it. And the auditor never said out loud that the winner was picked at zero cost; that is the next rubric rule.
